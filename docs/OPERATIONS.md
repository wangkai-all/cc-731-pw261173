# 运维手册

## 启动与目录

```bash
python3 -m app.server --root /srv/sparse --host 0.0.0.0 --port 8000
```

```
/srv/sparse/
├── repository.json          标签、来源、逻辑三元组、布局元数据、审计
├── layouts/
│   └── v<版本>-<布局>/      二进制数组（indptr/indices/kinds/data）
└── exports/                 已发布布局导出出的 .sparse 文件
```

服务只使用标准库、单进程多线程。`repository.json` 通过「写临时文件 + `os.replace`」
原子替换；数组文件按批 `fsync` 追加。

## 数据量参考

| 逻辑元素 | 单个布局数组 | 转换（512 B 批）| 核对 |
| --- | --- | --- | --- |
| 1 千 | ≈ 32 KB | 32 批 | < 0.1 s |
| 10 万 | ≈ 3.2 MB | 3125 批 | 数秒 |
| 100 万 | ≈ 32 MB | 31250 批 | 数十秒 |

- 批越大越快，占用内存也越多；`budget_bytes / 32 ≈ 每批元素数`。
- 核对是流式的，峰值内存与矩阵规模无关。
- 查询会按需把该布局的四个数组整体读入内存并缓存（最多 6 份），
  所以**读取端**内存约为 `32 × nnz` 字节。
- `repository.json` 保存全部逻辑三元组，大小约为 `80 字节 × 元素数`。
  这是刻意为之：逻辑层必须能独立重建任何布局。

## 中断与恢复

**网页**：「存储布局」页 → 对应布局 →「恢复」；或「开始 / 继续」。

**命令行**：直接重启服务。启动时会把所有 `building` 布局降级为 `paused`
（原因「进程重启」），进度与已写数组保留。再在网页点「恢复」即可。

**核对**：中断后恢复的布局仍需完整核对才会变为 `ready`。
「重新核对」可随时手动触发，核对失败会记录错误并保持不可读。

**磁盘满 / 写入失败**：转换线程会把布局标记为 `failed` 并记录错误，
已写入的部分保留。清理空间后点「开始 / 继续」（会重新从零开始该布局）。

## 常见问题

**查询报「布局尚未构建」或「已失效」**
说明该版本还没有通过核对的布局，或逻辑数据在布局发布后发生了变化。
到「存储布局」页重新转换即可，逻辑数据不会丢失。

**新增标签后旧布局全部变红**
这是预期行为：矩阵维度变了，`indptr` 长度必须改变。重新转换即可。
重命名、重排不会导致失效。

**导出文件下载后如何验证**
```bash
python3 scripts/verify_delivery.py deliverables/storage/v1-xxxx-csr.sparse
```
脚本只读文件本身，重新计算校验和，并按容器头重建 `indptr` 区间，
逐槽位比对坐标、类型与数值，同时检查标签表与形状。

**删除来源记录会丢数吗**
不会。数值与坐标保留，只是 `source_id` 置空，审计里记录「orphaned_elements」数量。
已发布布局不受影响（来源不参与数组编码）。

**两个数据版可以互相参照吗**
可以。标签是全局共享且编号稳定的，同一行标签在不同数据版里是同一个 `label_id`，
但坐标集合、布局、导出文件相互独立。

## 备份

停服务后复制整个 `--root` 目录即可（`repository.json` 与 `layouts/` 必须一起复制，
否则布局会因指纹不匹配被判定失效并需要重建）。也可以只备份 `repository.json`：
逻辑层完整，布局都能重新生成。
